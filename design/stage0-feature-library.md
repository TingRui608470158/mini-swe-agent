# Stage 0 — 共用 Feature Library（無 agent）

> 本文件是 [quant-trading-harness-architecture.md](quant-trading-harness-architecture.md) 「分階段 MVP」中 Stage 0 的細化說明。閱讀本文前請先讀過主文件，尤其是「核心設計原則」與「資料與評估設計」——本階段所有設計決策都是為了服務後面的階段，不是獨立存在的。

## 目標

建立**離線（回測/agent 研發）與線上（paper trading）共用同一份**的：

1. 歷史 K 棒資料的取得與清洗流水線
2. 特徵計算函式庫

「共用同一份程式碼」是硬性要求，不是效率考量：如果離線線上各寫一份，時區對齊、K 棒收線時間點、resample 邊界等細節不一致會導致「回測賺錢、實盤不像」——這正是 Stage 0 唯一要防的問題，也是後面所有 Stage 能否被信任的地基。

## 範圍

- 標的：BTC/USDT
- 頻率：1h bar
- 交易所：Binance/OKX 類（資料來源，非下單）
- **本階段不含**：策略、回測引擎（Stage 1）、晉升關卡（Stage 2）、agent（Stage 3）。Stage 0 完全是無 agent 的基礎建設。

## 交付物

1. **資料流水線**：固定時間範圍的 BTC/USDT 1h OHLCV 歷史資料，含取得與清洗（缺漏 K 棒、重複、亂序的處理方式需明確定義並記錄）。
2. **特徵函式庫**：point-in-time 正確的特徵計算，初版涵蓋報酬率、均線、波動度等基礎特徵即可，不需要一開始就齊全。
3. 對應「可驗收」四項標準的自動化測試。

## 設計要點

### 時間戳語意必須先定死

每根 K 棒至少有「開盤時間」與「收盤時間」兩個候選時間戳，且都可能被特徵計算或線上快照誤用。在寫任何特徵函式之前，先在程式碼與資料 schema 中明確定義：一根 1h K 棒的時間戳代表哪個時間點，且全程式庫、離線線上都必須一致。這個決定沒有標準答案，但一旦定了就不能中途更改，否則後面所有 Stage 的 parity 測試都會失真。

### Point-in-time 正確性（禁止 look-ahead）

任一時間點 `t` 的特徵值，只能使用「`t` 這根 K 棒收線為止」已知的資訊。任何用到未來 K 棒（哪怕只是下一根的開盤價）的實作都是 bug。這是 Stage 0 最容易犯錯、也最難事後發現的地方，因此可驗收標準裡專門有一項「平移一根 K 棒」的檢測（見下方）。

### 同一份程式碼、兩種呼叫模式

離線側是批次呼叫（餵一整段歷史資料，一次算出整段時間序列的特徵），線上側是逐筆呼叫（每來一根新 K 棒，只用「目前為止」的資料算出當下這一筆特徵快照）。函式庫必須讓這兩種模式走同一份計算邏輯，而不是各自實作一份、靠測試保證兩者一致——測試只能驗證一致性，不能保證它。實務上通常意味著：批次模式內部也是逐筆遞迴呼叫同一個「單點特徵計算」核心，而不是用整段序列的 vectorized 操作重新實作一次相同邏輯。

### Determinism

同輸入跑兩次，輸出必須逐位元相同：不能有隨機性、不能讀 wall-clock（`datetime.now()` 之類）、不能依賴字典/集合的不穩定迭代順序。這條規則會在 Stage 2 的純函數檢查裡被正式強制，但 Stage 0 就應該先養成習慣，避免後面回頭修。

## 可驗收標準

對應主文件原文，具體化為四個獨立的自動化測試：

1. **Determinism test**：固定一段歷史 OHLCV 資料（BTC/USDT 1h，固定時間範圍）與一組固定特徵，同一輸入跑兩次，輸出逐位元相同。
2. **Offline/online parity test**：同一份程式碼分別餵「整段歷史資料（批次模式）」與「模擬的即時資料快照（逐筆模式）」，兩者在重疊時間點上的輸出 schema 與數值必須一致。
3. **Look-ahead test**：把特徵整體往前平移一根 K 棒後重新計算，確認任何依賴未來資訊的實作 bug 會被這個位移操作暴露出來（即：平移後的輸出應該和「準確地晚一根做」的結果吻合，而不是巧合地不變）。
4. **Schema 一致性**：兩種呼叫模式（批次、逐筆）輸出的欄位名稱、型別、順序必須一致，方便 Stage 1 回測引擎與後續線上 Strategy Runner 直接消費同一個 schema。

## Out of scope（本階段明確不做）

- 策略邏輯、回測績效計算（Stage 1）
- 晉升關卡、資料切分權限隔離（Stage 2）
- agent 相關的一切（Stage 3+）
- 多資產（除了本文件範圍內的 BTC/USDT；跨標的驗證要等晉升前才用到 ETH/USDT、SOL/USDT）
- 真實交易所即時串接（Stage 5b 才需要；本階段的「即時快照」是用歷史資料模擬出來的固定測試案例）

## 完成後銜接

Stage 1（確定性回測引擎）直接把本階段的特徵函式庫當作輸入依賴之一：`策略(features) + 特徵(本階段產出) + 手續費滑價模型 → 績效報告`。因此本階段的輸出 schema 一旦被 Stage 1 消費，就等同凍結——之後若要改動特徵定義或 schema，需要連帶檢視 Stage 1 及以後所有依賴它的階段。
